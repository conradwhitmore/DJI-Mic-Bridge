# Mic Mini 2 音频设置：TX 与 RX 的边界

研究日期：2026-11-15。范围：官方 02.03.17.00 的 TX（3A）与 RX（5A）程序。本轮只做离线分析，没有连接设备、发送设置、修改固件或改动 App 功能。

TX 精确解包 SHA-256：`a65a40cddcdc1bd94d50e31976e9dbc515ea8eb11d51f9553a63ada2e083a199`。以下地址是该 TX/RX 程序的虚拟地址。不能将接收器 UI、命令名称或成功 ACK 单独当作发射器音效生效的证明。

## 结论

| 设置 | 固件中实际处理位置 | Mac 直连 TX 的判断 |
| --- | --- | --- |
| 声道设置 | RX `5B/01` tag `0008`，接收地址限定 `5A`，修改 RX 的声道配置与 `tr_usound` 路径 | 属于接收端输出/混音设置；没有找到对应 TX 直连设置。单个 TX 的 SPP 仍是单声道 |
| 增益调节 | RX 有自身增益档位及 TX 增益命令；TX 另有 ADC 和软件增益实现 | 存在底层能力，但现有普通 SPP `19/03` 仅改状态字节，不能当成已实现采集增益调节 |
| 监听增益 | RX tag `0026`，地址限定 `5A`，接收 -12…+12，调用本地监听增益函数 | 找到的是 RX 本地输出功能，没有找到 TX 直连的同义入口；Mac 监听音量应在 Mac 播放链路实现 |
| 音色预设：常规/饱满/明亮 | RX 将 UI 值转成无线命令；TX 自身保存 EQ 选择并加载采集 DSP profile | 有普通 SPP 控制路径，不必依赖实体 RX；本轮未做三档实机试听 |
| 降噪：关闭/弱/强 | TX 降噪开关与等级两个字段，应用到采集 DSP | 有普通 SPP 控制路径；开/关已在此前 Demo 验证，弱/强切换仍需实测 |

## 音色预设：普通 SPP 可达

TX `0x10021FC8` 的子命令跳转表将 `19/19` 路由至 `0x10022324`。这里先检查运行时型号必须为 1（Mini 2），随后比较现有 EQ，变化时调用 `spp_audio_set_eq`（`0x10022F60`）。没有要求对端必须是实体 RX 的名称检查。Mini 一代型号 0 会被此 SPP 分支拒绝，不能因为两代代码接近而给一代启用音色选项。

RX `5B/01` tag `0029` 的处理器 `0x1002CEFE` 把 UI 值加 1，再调用 `wl_msg_set_tx_eq`（`0x10012B78`）；后者发送无线子命令 `19`。TX 的 BLE 写配置处理器也把 tag `0029` 的值加 1。对应关系如下：

| 音色 | UI / BLE tag `0029` 值 | SPP `19/19` 值 | TX SPP 状态 `frame[15] & 3` |
| --- | --- | --- | --- |
| 常规 | 0 | 1 | 1 |
| 饱满 | 1 | 2 | 2 |
| 明亮 | 2 | 3 | 3 |

名称对应参考 [DJI-Mic-Control 的固定版本协议文档](https://github.com/ShadowBitBasher/DJI-Mic-Control/blob/9ba76880807a71d4eaba74c785dbee186a98f43b/PROTOCOL.md#commands)，加 1 转换及 TX/RX 调用链由本轮固件独立核对。

`0x10022F60` 只更改用户配置 byte[8] 的低两位，保留其他位。`0x1009778C` 结合低切开关生成 0…5 的 DSP profile：低切关时三种音色为 0/1/2，低切开时为 3/4/5。采集多音效开启时，`0x10022E40` 装载对应参数并调用媒体控制 `0x2F`、`0x18`。这不是仅变更 UI 状态的空分支；但实际频响、响度及算法配置可用性仍须录音对照。

TX `5B/02` 当前读取分派没有 tag `0029`，不能假设写配置后可用同 tag 回读；SPP 状态 `frame[15]` 低两位提供了更直接的观察入口。配置属于共享用户配置，正常关机保存路径可能使它持久化。

## 降噪：三态由两项设置组合

| 目标 | SPP 设置 | DSP 最终等级 |
| --- | --- | --- |
| 关闭 | `19/11 = 0` | 0 |
| 弱降噪 | `19/14 = 0`，再 `19/11 = 1` | 5 |
| 强降噪 | `19/14 = 1`，再 `19/11 = 1` | 7 |

`19/14 → 0x100224A8` 更新用户配置 byte[1]；若降噪已开，会立即重新应用。`19/11 → 0x10022434 → 0x10022D8C → 0x10022D4C` 将开关/等级解析为媒体控制 `0x39` 的 0/5/7。状态开关是 `frame[11] bit7`，等级是 `frame[15] bits5…6`。`19/14 = 0` 本身不是关闭降噪。

BLE 配置字段为 tag `000E`（开关）和 `001D`（等级），但其模式分支与普通 SPP 不完全相同，不能忽略模式条件，也不能假定 BLE 与 SPP 能同时稳定连接。本应用的 SPP 场景应优先验证无线控制入口。

此前 Demo 已验证 `19/11` 开关及状态回读，详见[降噪实测记录](MIC-MINI-2-KEY-EVENTS.md#11-demo-013-spp-降噪实测2026-11-14)。本轮没有增加弱/强实测结论。若未来加入 App 降噪控制，还需抑制自身设置引发的电源热键代理事件。

## 增益：有函数不等于普通 SPP 指令生效

- TX SPP `19/03 → 0x10022250` 只将参数写入 context `+0x18D`，随后返回接收循环；本分支没有调用 ADC 或软件增益函数。这个字段会被回读/上报，因此看到数值变化也不足以证明音频改变。
- TX BLE `5B/01` tag `0005 → 0x10024DF4` 在 `spp_audio` 模式下写状态、进行单位转换并调用 `spp_audio_set_adc_gain`（`0x10022CC0`）。底层检查采集对象、输入句柄及范围，存在拒绝路径；上层并未完整传播底层结果。此路径不能直接搬成普通 SPP 命令，且 BLE/SPP 并存限制尚未解决。
- `spp_audio_set_soft_gain`（`0x10022FD8`）有 -40…+30 dB 的参数范围并调用媒体控制 `0x49`。已定位到的调用来自初始化校准、shell 和工厂相关逻辑；没有找到可直接供普通 SPP 用户调节的同义命令。范围是底层函数能力，不是已确认的用户增益范围。
- RX `5B/01` tag `0005 → 0x1002C35E` 则接受 1…5 档并调 RX 本地函数。这与 TX 同号 tag 的语义不同，不能共用一套参数。

## 声道、监听增益是接收端设置

RX 声道 tag `0008 → 0x1002C3B6` 检查接收地址 `5A`，0/2 分支修改本地配置并进入 `tr_usound` 声道逻辑；值 1 在此分支被拒绝。TX 同 tag 进入 unknown-tag 路径，没有对应实现。

RX 监听增益 tag `0026 → 0x1002D026` 同样限定 `5A`，范围 -12…+12，写 RX 配置 byte[10] 并调用 `0x100238AC`。TX 写配置分派没有此 tag。以上仅说明本固件中找到的入口属于 RX，不把底层 SDK 中的通用 audio/channel 字符串当作 TX 已暴露的功能。

## 本轮离线验证与后续顺序

本机 ignored `work/mini2-audio-settings-20261115/` 保存 TX/RX 反汇编切片、`audit.py` 和 `audit-results.json`。42 项检查通过：包括命令表目标、两代 EQ 分支、三个音色和低切的 6 种 profile、EQ 设置保留其他配置位、降噪开关/等级到 DSP 参数、以及 SPP gain 分支只改状态。原 Thumb 指令在模拟 RAM 中执行，系统服务和 DSP 调用使用明确的替身；这不是整机模拟或声学验证。

## Mini 一代对照（2026-11-15）

另行检查官方 DM300 02.03.17.00 的 TX 和 RX。一代 TX 精确解包 SHA-256 为 `0ce8357318ef6fca5010e9e4d39fad4f537fff895467b20cf85b9cf6235241bf`。与二代 TX 的差异仍仅为 20 字节构建元数据，但运行时型号 0/1 的分支不可忽略；RX 程序不同，以下 RX 结果来自一代自己的镜像。

| 功能 | Mini 一代判断 |
| --- | --- |
| 关闭/弱/强降噪 | 有同样的普通 SPP 路径：`19/11` 控制开关，`19/14` 的 0/1 控制弱/强；处理路径没有 Mini 2 型号限制。一代硬件尚待验证 |
| 三档音色 | 普通 SPP `19/19` 明确拒绝型号 0；`le_audio` 的设置函数也拒绝一代。目前不能作为一代可用功能接入 |
| TX 增益 | 仍有 ADC/软件增益函数，但 `19/03` 仍只写状态；BLE 配置写入有 SPP 模式条件和单位/失败处理问题，未确认可用的普通 SPP 调节方式 |
| 声道设置 | 一代 RX 有本地输出设置；TX 未找到对应入口，直连单个发射器仍为单声道 |
| 监听增益 | TX 没有发现入口；一代 RX 对应的配置分支甚至只有日志/成功返回，不能照搬二代 RX 的实际监听增益实现 |

### 音色：算法存在，但正常入口限制一代

- SPP `0x10022324` 调用型号读取，只有值 1 才进入 `spp_audio_set_eq`；一代值 0 打印 `not suppotr eq` 并返回。
- `leaudio_set_eq`（`0x1001CDD8`）同样先检查型号 1；一代直接返回 -1，不修改配置。
- SPP 状态生成器 `0x10020AA8` 也只给型号 1 同步 EQ 状态字段；因此不能保证一代修改内部 EQ 后可从现有状态字段确认。
- 共享 TX 内仍有三档 EQ、与低切组合的六套 profile 选择逻辑；内嵌配置 `0x2B` 的有效值为 `01 06 02`，包含多音效启用配置。因此“普通入口不支持”不能扩大成“固件完全没有 EQ 算法”。
- 发现一个入口差异：BLE `5B/01` tag `0029` 在 **`spp_audio` 模式**下没有重复型号检查，条件满足时会把 UI 值加 1 后调用同一个 SPP EQ setter；在 `le_audio` 模式则调用有型号限制的函数。`spp_audio` 应用也处理 HFP，不能仅凭名称断言原生 HFP 不满足这个分支。实际应用模式与采集句柄仍需回读、实测，不能据此承诺一代无需修改固件就能使用三档音色。

### 一代 RX 的额外差异

声道处理函数 `0x10029220` 检查接收地址 `5A`，修改 RX 配置后进入 `tr_usound`；增益档位函数 `0x10029BD4` 同样限定 `5A`，接收 1…5 档后调用 `0x10023C9C`。

监听增益在两条配置处理分支 `0x1002AE66`、`0x1002B380` 中只读取数值、打印 `monitor_gain`，然后返回通用成功路径；没有看到二代 RX 中的范围检查、配置写入或音频应用调用。因此一代即使对该配置回复成功，也不能证明监听音量改变。

本机 `work/mini1-audio-settings-20261115/audit.py` 使用一代原始 TX 字节完成 49 项离线检查，包括型号 0 的 EQ 拒绝、BLE SPP 分支的入口差异、实际 SPP 降噪等级处理及 DSP 参数。外部服务仍为替身，无硬件连接或设置写入。一代可以优先实测降噪三态；音色与增益不纳入当前兼容承诺。

## BLE 增益继续核查（2026-11-15）

GitHub 的 `usokawa/dji-mic-mo` 在 Mini 2S 的 BLE 规则中提供 `transmitterGain`（tag `0039`）；这不是本节 Mini 1/2 的已验证实现，不能直接照搬型号或参数。

对 Mini 2 原始 Thumb 指令串联执行 `0x10024DF4` 和 `0x10022CC0`，发现上层、下层各做一次 ×10 转换。遍历全部 256 个有符号字节、两个应用模式，共 512 项：在有效采集上下文、句柄和底层成功返回的替身条件下，只有 `spp_audio` 中原始值 0/1/2 到达 `audio_record_set_volume`，四路数字增益参数分别为 0/100/200，状态字节成为 0/10/20。其余输入可能仍得到成功 ACK 或改变状态字节，但没有执行该音量调用。此结果不等于实机增益或声学响度验证，也不提供普通 ±12 dB 调节范围。

本机离线记录：`work/mini2-ble-gain-20261115/audit.py`、`audit-results.json`。Demo 0.1.7 只增加 `5B/02 tag0005` 增益回读与 `tag001C` 应用模式回读：模式 2 为 `spp_audio`，1 为 `le_audio`。没有加入增益写入按钮。配置回应必须匹配命令、序号、地址、tag 和长度。协议测试共 41 项（1 项跳过），其余通过。

首次实机准备中，MicBridge 收到 `12/65 ACK00` 后关闭 SPP；随后 BLE 完成服务发现即被设备断开，再连接超时、扫描未发现设备。因此此时尚无模式/增益回读结果，也未发送增益写入。待连接恢复后先核实实际模式，再决定是否进行可恢复的小范围音频对照。

### Demo 实机结果

设备重启恢复 BLE 广播后，FFF3 写入、FFF4 通知成功读取固件 `02.03.17.00`、模式 `2`（`spp_audio`）、增益 `0`。这证明 **RFCOMM SPP 未打开时也可能处于 `spp_audio`**，但不证明其采集句柄有效。

Demo 0.1.8 增加受限的 `0 → 1` 十秒短测：仅允许当前会话已验证版本、模式 2 和原值 0 的设备开始；十秒后请求写回 0 并回读。中断时保留原设备标识供手动恢复，不对另一台设备发送恢复命令。协议测试 42 项（1 项跳过），其余通过。本轮未改动生产 App 的增益功能。

- 15:49:28：`5B/01` payload `00 00 05 00 01 01` 收到匹配 ACK `00`；紧接着 `5B/02 tag0005` 回读 **1**，而不是离线完整底层成功路径的 **10**。因此 ACK 和状态变化不能视为采集增益成功。
- 15:49:38：自动发送恢复 payload `00 00 05 00 01 00`，收到 ACK `00`，回读 **0**。结束前再次回读仍为 0。
- 系统输入电平在后台不保证持续采集；现场只读 CoreAudio 快照曾显示 DJI 输入 running=1，但切换操作后的快照为 0。因此上面的写入不作为“持续 HFP 采集中调增益”的证明。
- 改用 QuickTime 固定 DJI 原生输入并持续录音后，CoreAudio 确认 DJI 输入 running=1、QuickTime input=1。此时两次模式回读均为 **0（既非 `spp_audio`，也非 `le_audio`）**。Demo 的增益短测因模式条件不符而禁用，没有在此阶段写增益。停止录音后模式重新回到 2。

当前结论：找到的 BLE tag `0005` 还不能作为 Mini 1/2 免 RX 有效增益功能。空闲时可进入处理分支但没有证实底层采集增益生效；持续原生 HFP 录音时实际模式又不满足该分支。没有进行有效的增益 A/B 声学对照，不能声称实测 +10/+20 dB。用户提供的官方页面明确标为 **RX 设置**，其中五档“增益调节”和 −12…+12 dB“监听增益”属于 RX 控制入口，不能映射为当前 TX 指令的参数承诺。

本机研究目录保存模式回读、短测日志摘录、CoreAudio 快照和 33 秒 `hfp-mode-check.aifc`（仅确认持续采集模式，不是增益对照样本）。结束时退出 BLE Demo、恢复 MicBridge SPP 收音。没有刷写固件、改变降噪/音色，或推送仓库。

## TX 增益入口的进一步追踪（2026-11-15）

结论更新：**不能将 BLE tag `0005` 的 0/1/2 限制解释为 TX 只具备三档增益。** TX 有更细的本地调节函数，也有值得实测的独立蓝牙音频调试入口。以下依据精确解包 TX SHA-256 `a65a40cddcdc1bd94d50e31976e9dbc515ea8eb11d51f9553a63ada2e083a199`，本轮未向设备发送指令。

### 本地 shell 与实际采集增益

- `api_set_adc_gain → 0x100114B4`：在 `spp_audio` 分支接受整数 −12…+12，加 12 后调用 `0x10022CC0`。底层再乘 10，送至 `audio_record_set_volume (0x1003B8DC)` 的数字增益为 0…240，步长 10；模拟增益置 0。这条路径没有 BLE tag0005 的双重 ×10 问题，也没有在该调用链写入属性存储。
- `api_set_mic_gain → 0x100229F8` 直接调用同一 ADC setter。固件帮助字符串描述为 `set mic gain range 0~24db unit 0.1db`，但实际函数包含 ×10，不能直接按字符串给用户定义单位。
- 这些是固件中的 shell 命令，不是已验证可以通过普通 SPP/BLE 直接发送的命令。−12…+12 是 shell 输入范围；零点偏移、实际声学增益尚未标定。
- HFP 的 `btcall_set_adc_dgain (0x10015D28)` 也存在；目前追到的调用来自 ALC 开关：启用/禁用分别传入 0/13，尚未证明能通过现有用户 BLE 配置做任意数值调整。

### 独立工具 SPP：可到达采集增益的候选入口

此前按键研究识别过的工具服务 UUID `0000e004-0000-1000-8000-00805f9b34fb`，在这次增益分析中找到具体用途：

`SPP 工具接收 → 90 / ABTP → as (0x7361) → config_protocol_adjust (0x1001A8E0) → 配置 0x37 → audio_system_set_microphone_volume (0x1003C3DC) → audio_record_set_volume`

- 服务配置位于 `0x100B6FA0`，UUID 原始字节位于 `0x100C6304`；`spp_test_app_init (0x10018EBC)` 注册后，连接回调启动独立工具线程。固件有注册路径不等于实机当前一定提供该服务，也未验证能与收音 SPP 同时保持。
- `0x37` 要求捕获 player 类型位有效。它会把交错的 4 组模拟/数字增益重新排列成底层结构，并调用采集音量函数。该函数实际遍历全局两个录音句柄，没有按传入 stream type 过滤；不能假定只影响某一个音频对象。
- 存在需要先处理的协议布局问题：配置字段要求 `size == 10`，但该分支实际读取 **16 字节**，并将数据偏移 8 的字节同时用于另一音量调用。不能发送仅有 10 字节的增益内容，也不能照猜测构造实机包。离线使用完整 16 字节数据，仅用于验证代码路径，不作为推荐参数。
- ABTP 的 `AT` 分支通过 `0x1009CBC6 → 0x100A6F32` 转发消息 `CC/53`。目前不能把它认定为执行上述 shell 命令的隧道。

因此，下一步优先只查询实机 SDP，确认 `e004` 是否公开及其 RFCOMM 通道；再核对完整协议、原增益读取/恢复方式与收音共存条件，最后才做可恢复的音频对照。不要把工具包发送到现有普通音频 SPP 通道。

### 持久化校准不是普通音量控制

命令表还注册 `50/07 → 0x10023CB4`、`50/08 → 0x10023AA8`、`5B/07 → 0x10023D58`：

- `50/07` 将 payload 浮点值转整数，保存并刷新 `MIC_CALI_GAIN`，随后按当前应用尝试应用软件增益；保存发生在底层范围判断之前，成功 ACK 不证明实际应用成功。
- `50/08` 读取该属性并返回 4 字节浮点值；这是校准属性，不是当前 ADC 增益的直接读回。
- `5B/07` 对应 tag0005 的路径同样保存校准属性，但没有在该处理函数立即应用增益。
- `spp_audio` 初始化读取校准值后还存在取负并限制至 −3…+3 的处理，不能把校准写入当作普通 −40…+30 增益滑块。也未证实这些通用表命令可从当前普通音频 SPP 分派触达。

本轮没有执行任何校准写入。`work/mini2-gain-entrypoints-20261115/audit.py` 对原 Thumb 指令完成 **37 项离线检查**：29 个 shell 输入（含边界拒绝）、6 组 ABTP/配置/采集音量完整调用路径、AT 转发及 UUID 检查。平台、录音对象与传输读取由替身提供；这证明代码路径与参数转换，不证明实机服务可达或实际响度变化。MicBridge 与 Demo 功能均未改动，未构建、未刷固件。

## Mini 1/2 TX 的 BLE tag0039 核查（2026-11-15）

针对 `usokawa/dji-mic-mo` 中 Mini 2S 的 `transmitterGain` 路线，检查 Mini 一代和 Mini 2 的官方 **02.03.17.00 TX**：**两者的 BLE 配置读写均不支持 tag `0039`**。这不是仅依赖开源项目的型号限制推断。

- 开源 BLE 实现将 `transmitterGain` 放在 `RULES_MINI_2S` 中，写入走 `5B/01`、tag `0039`。普通 Mini 的规则表没有这项。
- TX 命令注册：`5B/01 → 0x10025360 → 0x10024AD0`；`5B/02 → 0x10025678 → 0x1002536C`。
- 写配置在 `0x10024C94` 读取 16 位 tag。`0039 > 0010`，走 `0x10024B4E` 的高 tag 分派；此路径只显式匹配 `001C/001D/0022/0029`，`0039` 落入 `0x10024B62` 的 `unknown tag`，最终单字节回复 `FF`。不会进入 `0005` 的 ADC 增益路径。
- 读配置在 `0x100253F2` 读取 tag。大于 `0010` 后仅匹配 `001C/001D`；`0039` 落入 `0x10025430` 的 `unknown tag`，单独查询最终也回复 `FF`，没有增益数值。
- 两份 TX 的完整读写处理区间 `[0x10024AD0, 0x10025684)` 逐字节相同，以上分派在到达应用模式/型号判断之前就已拒绝 `0039`。

`work/mini-tx-tag0039-20261115/audit.py` 使用两份固件原 Thumb 指令，分别执行 `5B/02` 读取和 `5B/01` 写入 −12、−1、0、1、12，**12 个离线用例全部得到 unknown-tag 日志及 `FF` 回复**。日志、内存复制和回复传输使用替身；没有调用蓝牙、没有向设备发送写入。脚本还核对命令表和两代处理区间相同。完整镜像哈希见其 `results.json`。

固件中的其他 `0x39`（例如内部降噪 DSP 控制编号）与 BLE 配置 tag `0039` 属于不同命令空间，不能作为支持该增益 tag 的证据。结论范围限于已检查的两代官方 02.03.17.00 TX，不扩展到 Mini 2S 或未来版本；当前无需通过实机盲写 `0039` 来验证同一个拒绝分支。

### 写入链路

`usokawa/dji-mic-mo` 的 Mini 2S 路线与原固件一致：

1. `5B/01` 注册入口 `0x1002A4D4` 跳到 `set_audio_params_process (0x1002955C)`。
2. 此版本要求参数头版本 **2**，完整包的 byte[11] 为 `02`；tag 在 byte[16:18]，长度在 byte[18]。Mini 1/2 的旧格式将 tag 放在 byte[13:15]，两者不能直接混发。Mini 2S 的增益 payload 为 `02 00 00 00 00 39 00 01 GG`，`GG` 是有符号 8 位整数。
3. `0x10029670` 的跳转表把 tag `0039` 路由至 `0x100296FE`：要求长度 1，使用 `ldrsb` 读取增益；对 TX 地址 `3A/7A` 发起 `dm_user_setting_modify_request (0x100A275C)`，参数为 user=3、event=1、value=增益。此分支没有要求连接实体 RX。
4. 队列消费者 `0x100A222C` 将 event=1 路由至 `0x100A24A4`，把有符号增益转为 float，然后调用 `dm_us_apply_set_tx_post_gain (0x100A1414)`。
5. 后者分别以 type=2、type=1 调用 `HD_audio_ux_manage_gain_set (0x1002D614)`，继续进入 **`HD_audio_alg_sw_gain_set (0x1002B5F4)` 软件增益模块**；随后保存有符号增益到用户配置 `0x210059C6`，调用 `user_setting` 存储路径。

因此，这条命令调的是 **TX 后级数字/软件增益**，不是直接操作 ADC 模拟前置增益。状态组包在 `0x1002AA68` 通过 getter `0x100A0B90` 读取同一配置值，保存到状态字段，和开源 BLE 规则读取有符号增益的方向一致。尚未逐字节验证完整状态包布局，不把它视为声学效果回读。

开源客户端将范围限制为 **−12…+12 dB、1 dB 步进**。本轮追踪的固件命令处理、队列消费者和后级入口没有发现相同范围检查，因此该范围应描述为客户端支持范围，不能说固件已验证拒绝其他值，也不应据此扩大设备写入范围。

### 离线执行验证与边界

`work/mini2s-firmware-20261115/audit_gain.py` 执行原始 Thumb 指令，完成 **20 项离线检查**：

- −12、−1、0、1、12 在参数头版本 2 下均进入 event=1 请求并收到 `00`；同布局仅把版本字节改成 0 时均返回 `FF`。
- 队列消息中的整数增益无缩放地转为 float，进入后级增益入口。
